## C01. Foundation and product loop

Delta is a standalone SillyTavern extension built from `kohz87/npc_state`, commit `a12b2937b5c1305e3e3017218a626478a5bedcdc`, directory `legacy/v0.2.x`, manifest version `0.2.23`. The seed includes the retained 0.2.18 engine and later hardening/enhancements actually present in that snapshot. Do not substitute another 0.2.x revision based only on its name.

The essential loop is: completed story exchange -> legacy-style dedicated scan -> grounded dossier update -> owned persistence/checkpoint -> relevant accepted continuity in the next roleplay request. Use legacy as the main implementation and behavior base, with selected Beta/Alpha features adapted into it. The nine phases are work stages, not nine runtime components or alternate operation modes.

No mandatory machine trailer in roleplay output, no separate mandatory Immediate/Development architecture, and no independent background dossier database. No dependence on installed legacy/Beta/Alpha extensions or their settings/data. Delta does not add an always-on server worker. The opt-in one-pass narration capture amended under C03 is optional, default off and never required for the loop; with it off no roleplay output is requested or parsed.

## C02. State, settings and namespace

Maintain one canonical per-chat dossier state, one settings source, one persistence/checkpoint path and one relationship mechanics implementation. UI projections are reads of that state, not additional authorities.

Use the `npc_state_delta` installation/settings identity, `NPCStateDelta` public global and Delta-specific DOM, prompt, sidecar, recovery, writer-lock and bundle identifiers. Do not automatically discover or migrate another generation's data. Internal historical-shape readers retained in the seed are not a product promise of generational import support.

Application versioning is one synchronized release concern, separate from persisted schema/version families. The current application version is recorded authoritatively in `manifest.json` (`version`), `package.json` (`version`), `runtime-modules.json` (`applicationVersion`), `core.js` (`NPC_STATE_VERSION`), and the `bootstrap.js` version banner. Release-facing current-version derivatives are the README title/installable package name, the current release section in `DEVELOPMENT.md`, the top release entry in `CHANGELOG.md`, and current-version assertions in tests. Manual follow-up controls remain task-owned and lifecycle-stable: the global `Scan dossier now` action and the settings-level manual `Full scan current cast` action belong to Data & maintenance even when extension modules render out of order, with the full-cast action ordered immediately before `Clear chat dossier`; optional automatic full-cast configuration belongs to Scanning, and the Diagnostics modal may expose its own manual `Full scan current cast` follow-up action only by delegating to the canonical `full-cast.js` owner. Portrait generation must not absorb unrelated maintenance/scanner actions. Per-NPC portrait seed is optional manual image-generation metadata only: nullable by default, never scanner-written or roleplay-injected, normalized to a non-negative JavaScript safe integer when present, and passed only through the host image-generation seed override. When the field is blank, Delta may choose a fresh preview-scoped safe-integer seed before dispatch so the exact seed used for that preview can be shown and explicitly saved; preview seed provenance is not canonical NPC state until that save occurs. It must not move model/workflow/sampler/resolution ownership into Delta. Canonical NPC gender is separate stable identity metadata with exactly two stored values, `male` or `female`; blank means unknown/not yet established. Automatic capture requires explicit story wording or an unambiguous gendered identity/reference and must never infer gender from a name, occupation, clothing, body type, species, or generated portrait. Once established it is keep-by-default; an automatic conflicting value requires explicit correction state/reason. Dossier presentation orders Species · Gender · Role before age cues, and portrait identity sends species then gender before apparent age/appearance/role. Every application release candidate must update all current markers together and validation must reject disagreement. Bundle, branch-lineage, diagnostics, storage, rollback-journal, and other persisted format versions remain independently governed and are never bumped merely because the application version changes. Historical review documents, migration fixtures, old-version regression names, and provenance records must retain the version they actually describe; never perform a global historical version replacement. Unreleased implementation work may remain on the current application version until release preparation is explicitly authorized, but it must not introduce a competing version marker.

Preserve the original repository GPL license and source provenance. Runtime must be self-contained. No GitHub/network source loading from reference projects.

## C03. Capture, scanner and routing — stage 3

Retain legacy's completed-message capture, latest-exchange routine scan, configurable scan cadence, manual Scan/Refresh, configured history modes, conditional focused relationship passes, malformed-response handling and necessary backfill behavior unless a task explicitly changes a path. Preserve source/branch ownership and late-result rejection. No Beta-style requirement that an owning scan must succeed before another ordinary generation may proceed.

Each valid assistant story receipt owns one deterministic turn/cadence increment at its actual raw-message boundary, independently of scanner success. Journal it before asynchronous scan dispatch; successful processing may safely consolidate at the same boundary. User/system/empty messages and duplicate receipt events do not increment turns. Failed, skipped, busy, canceled or delayed scans do not manufacture dossier updates, absence or lifecycle cleanup, nor transfer receipt changes to a later user boundary.

The seed's message handler awaits scanner work; retaining it is not a guarantee of nonblocking host behavior. Measure generation wait and provider contention separately. Do not introduce new waits or advertise foreground priority without verifying the actual selected host route.

Add a scanner connection-profile setting. An empty/default selection uses the existing host route. A selected route applies consistently to retained NPC model requests: automatic/manual scan, targeted Refresh, focused passes, repair/retry and applicable backfill. Ordinary roleplay keeps its configured route. Portrait generation remains its own host image workflow.

A missing/unavailable selected profile produces a clear recoverable error; never silently route to a different provider/model. Prefer request-scoped routing. Any temporary host setting changes must restore reliably and cannot redirect concurrent roleplay. One shared dispatcher should account for actual request counts, timeouts and cancellation. Do not add automatic completeness calls or additional passes solely to compensate for a larger contract.

Automatic post-scan repair is target-scoped. If the broad scan explicitly misses one existing NPC genuinely participating in current narrative exchange, Delta may queue that dossier for silent continuity repair. Structured World State, NPC Inner Chatter, roster/status blocks, or other evidence-only listings do not by themselves establish participation or authorize an established-dossier repair. Automatic repair queue entries are versioned, reason-scoped transient work owned by one source exchange; legacy/unversioned persisted entries are discarded on normalization, and `missed-participant` work must be revalidated against its owning exchange before dispatch. Automatic omitted-established-participant repair is bounded to at most one target per broad scan; multiple apparent omissions suppress that per-NPC fallback rather than becoming an implicit full-cast pass. A newly created or promoted dossier may receive its own targeted recent-history enrichment. New admission alone must never fan out targeted backfill requests across unrelated established active dossiers; the inherited v0.2.23 cast-wide topology sweep is intentionally retired. Manual Refresh/Scan and the separately opt-in current-cast scan remain explicit operations with their own scope.

## C04. Dossier establishment and evolution — stage 4

Retain identity/admission, aliases, role/species, actual/apparent age, durable Home Base / Usual Location, live state, personality, behavior profile, characteristic speech, mannerisms, background, memories, non-player ties and bounded profile-evidence evolution. Home Base is ongoing-life geography such as a home, workplace, headquarters, or regular haunt and is distinct from live Location; a temporary scene location cannot silently replace an established Home Base. Supported new facts can populate the first scan. Unknown fields stay unknown; do not infer merely because a field is blank. Omitted fields preserve accepted values.

Retain legacy refinement/evolution rules and the separation of durable identity, transient mood/condition, player-specific dynamics, and profile evidence. Do not silently replace its heuristics with Beta/Alpha's evidence contract during cleanup. Explicit later changes require a recorded behavior decision and tests.

Behavioral Profile is a bounded current set of target-general behavioral levers that translate durable identity into response/decision tendencies. Observed actions are evidence for those levers, not an action-history format. Labels are a soft semantic taxonomy, never mandatory slots: compatible names may consolidate into families such as Disposition, Cruelty/Mercy, Independence/Agency, Care/Warmth, Expressiveness, Conflict/Assertiveness, Threat Sensitivity, Analytical Style, and Social Presentation, while unknown supported labels remain allowed. Temporary anxiety or stress remains live Mood/Status unless established as a durable cross-context tendency; player-specific behavior remains relationship continuity; verbal production belongs Speech and recurring physical habits belong Mannerisms. Do not create empty/default Behavioral Profile categories merely to fill the taxonomy.

User-authorized Delta 1.1.6 amendment: settings may name up to six custom fields (for example Level or Class), tracked on every dossier as short text values. They are keep-by-default: a scan, Refresh or backfill sets a configured field only when the scanned source text carries the value, omission keeps the stored value, an established value changes only with a stated reason, unconfigured names are ignored, and a manual lock protects them. With no fields configured, prompts and requests are unchanged.

Durable profile summaries are CURRENT state, not history containers. When the scanner explicitly supplies an accepted `refine`, its full Personality, Speech or Appearance field and full bounded Mannerisms/Behavioral Profile list are authoritative after the existing safety/admission gates pass; omitted superseded clauses/rules retire instead of being appended back. Missing/`keep` lifecycle markers do not inherit that destructive full-summary authority: compatibility recovery may add grounded detail only when it preserves every established durable concept and also passes the field's normal safety gate. Personality morality conflicts and Speech evolution language remain disallowed on this path; lexical repetition inside negation such as `no longer` is not preservation of established meaning. Profile evidence, memories and their existing history owners retain longitudinal support separately. Unsafe full Behavioral Profile refinement rejects atomically and preserves the established profile. Protected agency/morality direction is evaluated across the whole proposal without collapsing mixed positive/negative evidence to neutral, including reversals hidden behind renamed categories and bounded negation such as `not independent`; ordinary cooperation or contextual mention of authority alone is not obedience. The same explicit-refine rule applies per appearance slot: accepted overall/named-form refinement replaces that slot's current summary while unrelated named forms remain preserved; unmarked/`keep` form updates cannot retire omitted established detail. Delta 1.0.28 additionally requires newly introduced durable meaning in runtime `refine`/recovery paths to be grounded in the supplied field evidence/story source rather than authorized by overlap with established wording alone; directly grounded clarification may still apply on first observation without being forced through gradual-development readiness. Mannerism and Behavioral Profile collection order is presentation-only, so reorder alone is not semantic change and cannot consume evidence. Evidence resolution is claim-body based, including polarity, and a matching concept label alone never proves that an observation is already represented. Delta 1.0.29 makes that admission claim-complete and target-NPC-specific, applies it consistently to flat Appearance reconciliation, evaluates evidence representation directionally, scopes negation/polarity to the relevant claim unit, requires explicit per-member proof before already-resolved bonds inherit collective semantics, and preserves copular/visibility/negation grammar when Shared appearance prefixes are deduplicated. Delta 1.0.35 permits one additional non-destructive recovery for established Behavioral Profile: a missing/`keep` state may admit only additive target-general rules when the returned full candidate preserves every established rule verbatim, every new rule is grounded by Behavioral Profile evidence, and the existing agency/morality conflict guards pass; omission never retires or rewrites established rules. Scanner and targeted Refresh extraction may place the same scene into multiple durable-field evidence arrays when it independently supports each field, including Speech and Behavioral Profile. Manual locks remain authoritative. User-authorized profile evolution also distinguishes narrative provenance: declarative user-authored canon may authorize grounded explicit or elapsed batch development immediately, while assistant/main-speaker prose remains observational evidence even when it describes itself as permanent. Questions, speculation, requests, conditionals, future wishes, and fully quoted user dialogue do not receive declarative canon authority. Corrupted legacy entries must still be removable when their structured subject prefix uniquely identifies the counterpart. ## C05. Terminal automatic death — stage 4

Retain grounded legacy lifecycle detection but remove automatic narrative reactivation/resurrection. Once confirmed dead, later model/structured/Refresh output cannot make the NPC alive or currently active again. Preserve historical identity, dossiers, memories, relationships and portrait references. Death does not delete the record.

An explicit user correction can repair an erroneous death. Delta may use the retained manual Restore control for that correction as long as it records correction provenance and does not infer current presence; it is not narrative resurrection. Owned-history rollback can remove a death whose source was deleted, edited or abandoned by a swipe. These are corrections of invalid state, not a narrative revival feature. They must not revive unrelated dead NPCs or bypass provenance. All automatic writers obey the same terminal rule.

Automatic stale lifecycle uses assistant-turn inactivity: defaults archive at 30 and delete at 50 since the later of lastSeenTurn and lastWorldActiveTurn. It runs only after a successful eligible scan with auto-pruning enabled (including the existing capacity-gated path), never merely on message receipt or scan failure. Present, world-active, retention-protected and scan/transcript-referenced NPCs are exempt. Only stale automatic archives participate in timed deletion; manual and death archives remain protected. A living unarchived dossier already beyond 50 turns may be removed directly with structured social/reference/pending-work cleanup. Explicit terminal death is protected independently of archive status, including when automatic death archiving is disabled: retain the dossier, history and references until explicit user removal or owned rollback invalidates the narrative record. Reuse the shared terminal policy.

## C06. Relationship scoring — stage 5

Retain the exact pinned legacy mechanics and interpretation as the initial Delta policy. Four independent NPC-to-player axes: Trust, Affection, Desire, Tension; default baseline zero; integer range -100..100 with separate signed fractional progress.

| Impact | Default maximum raw magnitude per axis | Maximum axes |
| --- | ---: | ---: |
| none | 0 | 0 |
| ordinary | 1 | 1 |
| meaningful | 2 | 2 |
| major | 5 | 3 |
| extreme | 10 | 4 |

For outward movement, multiply raw capped evidence by the legacy magnitude bands: `<30:1`, `<50:0.75`, `<70:0.5`, `<85:0.35`, `<95:0.2`, otherwise `0.1`. Movement toward neutral retains legacy's impact-sensitive resistance; extreme contrary evidence acts at full raw strength. Accumulate fractions before converting to whole displayed movement. Do not round away progress or reweight the model's proposal twice.

Gates are per axis and direction at 25/50/75/90, requiring meaningful/major/extreme/extreme respectively and stock minimum raw magnitudes 1/3/5/8. Retain legacy's configured-cap adjustment to gate minima. Reaching a locked boundary does not bank outward fractional progress; a qualifying event can unlock it even without an immediate visible point. Existing unlocked milestones, progress and reasons survive ordinary persistence and valid recovery.

Retain legacy overflow selection, including rejection of an ambiguous equal-weight tied group; retain its evidence and duplicate handling at baseline. Beta's priority tie handling/source-event duplicate refinements are optional discussion items, not approved changes. Do not substitute Beta's resistance curve or Alpha's default +/-1000 score scale, zero inertia, descriptive milestones, or absence of legacy event caps.

Score genuinely new directional evidence, never repeated narration of the same event. Desire needs its own grounded support; warmth, rescue and trust alone do not establish it. A zero numeric change may still update an appropriately grounded relationship description. Identity, agency, boundaries and other bonds dominate player relationship expression. Manual corrections and owned rollback must preserve the intended per-axis state; historical scans cannot replay old score events as new ones.

## C07. Evidence and roleplay injection — stage 6

Retain legacy narration, supported World State/Inner Chatter and explicit dossier-source handling. Do not import Beta/Alpha's narrower structured-source permissions by accident. ## C08. Persistence, history and removal of OOC commands — stage 7

Retain legacy sidecar storage, owner-qualified chat keys, lineage/swipe-aware snapshots, writer locking, revision conflicts, dirty-write retention/retry, recovery copies, deletion tombstones, rename/delete lifecycle handling and branch recovery. The SillyTavern server-side sidecar is the only canonical persistent authority for a chat. Browser memory, UI projections, editor/portrait drafts, scanner state, branch helpers and other caches are ephemeral working state: hydrated does not mean fresh. Sessions sharing the same SillyTavern backend must verify the durable sidecar revision plus writer identity at meaningful lifecycle and mutation boundaries rather than polling continuously; a clean stale cache rehydrates to the newest durable revision, while a dirty stale cache preserves recoverable local work and fails closed instead of overwriting or blindly merging with the newer server state. Long-running provider/portrait work must retain its durable base revision and reject completion after that base advances. A freshness inspection must never grant the stale local copy the newer revision token before conflict policy decides whether the working state is clean or dirty. Separate SillyTavern servers are independent stores by design; Delta does not add localStorage/IndexedDB authority, cloud synchronization, peer-to-peer synchronization or device-specific canonical copies. Full branch checkpoints remain byte-bounded recovery/swipe anchors. Delta 1.0.12 retains up to 8 MB of full checkpoints with a 2 MB ceiling per snapshot and independently versions a one-time legacy branch-history compaction. Compaction may retain only the current active lineage plus alternates still proven by SillyTavern's swipe state, and may drop unreachable sibling checkpoints/cards and rollback-journal chains not owned by the live head or a retained checkpoint. It must defer while destructive divergence remains unresolved, then retry after reconciliation; compaction cannot shorten the advertised active rollback-journal horizon. Delete/regenerate and message-edit events are linear replacement operations. Their destructive recovery target is exactly the surviving parent boundary at `divergence - 1`: restore it only from journal proof or an exact checkpoint, discard recovery artifacts owned by replaced descendants, and never substitute an older retained checkpoint or generic root for a missing parent. Near-tail replacements with at most one affected assistant exchange may rebuild from that exact parent and rescan the replacement; if multiple assistant descendants remain after a deep edit, preserve the current canonical dossier state and fail closed rather than rewinding later accepted continuity that cannot be deterministically replayed. Only explicit SillyTavern swipe events authorize sibling-branch retention. A known swipe may restore an exact sibling; an unseen swipe may use only its exact parent/root anchor and must then rebuild the new sibling. Destructive lineage identity is narrative-content based; mutable host `send_date`, generation ids and swipe indexes may assist host interaction but cannot by themselves authorize canonical rollback. The reversible journal owns chronological rollback and, in Delta 1.0.8, guarantees a contiguous 256 raw-message horizon from a trustworthy baseline using message position together with lineage identity. Recovery must distinguish same lineage, harmless forward extension, strict tail truncation and replacement divergence; a persisted lineage that is merely an exact prefix of the live chat cannot restore an older checkpoint. If no exact/proven target exists for a divergence, recovery fails closed by retaining the accepted canonical dossier and rebasing current ownership rather than walking backward to an older checkpoint/root. An explicit first-message swipe may still use its pre-message root anchor because the host has authoritatively declared alternate-branch semantics. Unchanged user/system boundaries must remain traversable even without undo mutations, and repeated same-message commits may coalesce only if their lineage ownership matches and referenced journal versions remain immutable. A retained descendant or a checkpoint other than the same boundary being replaced owns its sequence and required predecessors; coalescing must use copy-on-write when referenced, including fields returning to their original values and net-zero changes. Retained checkpoints keep their required predecessors within the proven message horizon; optional sibling retention cannot strand a retained chain. Journal rollback reverses structural state as well as fields: an NPC introduced only in deleted history disappears together with owned social references and pending work, while surviving NPC state returns to its prior narrative values. Social-graph undo should retain changed edges/slots rather than whole prior graphs where stable identities permit it. Existing user-owned metadata overlay/tombstone rules remain authoritative and cannot resurrect a narrative NPC whose existence was rolled away. Dirty local state that failed persistence cannot be silently replaced by an older sidecar after bounded-cache eviction; the persistence owner retains the newest accepted undurable snapshot until a later successful write or explicit authorized cancellation/removal. Hydration from any unsaved recovery source cannot establish durability. Every persistence failure exit, including transition from transient retries to permanent rejection, must preserve recoverable pending state or honor an explicit cancellation/retirement/ownership invalidation. Recovery cannot overwrite newer accepted in-flight mutations, bypass a remote revision conflict, or resurrect canceled data; bounded lifecycle transaction failures remain with their existing transaction recovery owner. The journal contains no transcript text and performs no model reconstruction. A numeric message position alone is not durable ownership; bytes may be diagnosed/limited for optional history but cannot silently invalidate an advertised active rollback horizon.

Remove narration-based OOC commands and command-only parser/listeners/exports/help/tests/backfill dependencies. Keep manual UI/API editing, add/remove/archive/restore as appropriate to terminal-death rules, locks, portrait handling and suppression safety. Trace shared dependencies so removing OOC does not remove ordinary scan or manually requested repair.

No automated operations on actual user databases during development. Import/recovery operates on its declared target and cannot cross an unproven history boundary or silently overwrite another chat.
